# VLM Grounding Experiment — Annotated Recognition Image

**Fixture:** `c658e915-9247-4904-8032-717dd11ecfdd.jpg` + `recognition-c658e915-9247-4904-8032-717dd11ecfdd.json`
**Model:** `gpt-5.6-luna` (OpenAI, structured outputs via `zodResponseFormat`)
**Branch:** `feat/vlm-annotated-grounding`
**Debug page:** `/debug/floorplan-recognition`

## Question

*Does an annotated raw-recognition image (labels `wall-*`, `door-*`, `window-*`, … rendered
over the original image) significantly improve VLM object-ID grounding?*

## Method

- **BEFORE (baseline):** `before-single-image.json` — POST to
  `/api/debug/floorplan-recognition/vlm-analysis` with **only** the original image + raw JSON
  (the previous POC behaviour; the endpoint still supports this path).
- **AFTER (annotated):** `after-annotated-run1.json` / `after-annotated-run2.json` — the same
  endpoint driven through the real `/debug/floorplan-recognition` page, so the annotated image was
  generated by the actual frontend renderer (`frontend/lib/annotated-recognition-image.ts`) and
  sent as a second image alongside original + raw JSON. Two runs capture VLM variance.
- Ground truth for "correct ID" was derived from the raw geometry itself
  (`raw-geometry-summary.txt`: per-object bounding boxes in image pixels).

## Annotated image verification (before calling the VLM)

`annotated-recognition.png` (1500×1060, full source resolution, same coordinate system):

- every raw object bbox shows strong overlay presence (18–76 % changed pixels, see
  `annotated-pixel-probe.json`) → overlays/labels are drawn at the correct raw coordinates;
- global change rate is only **7.77 %** → the annotated image stays visually close to the
  source (semi-transparent overlays, architecture still readable);
- category-specific colors + always-on ID labels (`wall-0…4`, `door-0…5`, `window-0…4`,
  `entry_door-0`, `kitchen-0`) are rendered from the RAW JSON only (no normalize/rooms/3D code).

### window-3 (kitchen window) — the clearest grounding win
Geometric ground truth: window-3 spans x309–429; `wall-3` starts at x=433, so its only possible
host is **wall-4** (the west/top-left wall system).

|             | host claimed      | confidence                                                                                                  | verdict |

| BEFORE      | `wall-3` 0.94     | ❌ geometrically impossible (wall-3 bbox starts at x=433, window ends x=429)                                 |
| AFTER run 1 | `wall-3` 0.93     | ❌ same error                                                                                                |
| AFTER run 2 | **`wall-4` 0.76** | ✅ correct, with explicit reasoning ("north exterior wall, whose left-side segment is identified as wall-4") |

### False positives
|                                  | BEFORE      | AFTER                                                                             |

### Uncertain behaviour (new)
- `window-1` host: `uncertain`, confidence **0.08–0.18** instead of guessing.
- run 2 emitted an explicit second, low-confidence entry for door-0 (0.30, "exact host segment
  ambiguous") instead of a single overconfident guess.
- run 1 connection `wall-0 + wall-1 → uncertain 0.42` where the entrance/windfang gap is
  architecturally unclear.

### ID grounding accuracy per opening (checked against raw bboxes)
| opening                | BEFORE               | AFTER run 1                    | AFTER run 2                                             |
| ---------------------- | -------------------- | ------------------------------ | ------------------------------------------------------- |
| window-2 → east facade | wall-3+wall-1 ✅      | wall-3+wall-1 ✅                | wall-3+wall-1 ✅                                         |
| window-3 (kitchen)     | wall-3 ❌ (0.94)      | wall-3 ❌ (0.93)                | **wall-4 ✅ (0.76)**                                     |
| door-0                 | wall-4 ✅ (0.78)      | wall-0 ❌ (0.90, overconfident) | wall-0+wall-4 ✅ + uncertain 0.30                        |
| door-5                 | wall-2 only          | wall-2 only                    | wall-3+wall-2 ✅ (both segment portions, matches bboxes) |
| entry_door-0           | wall-1+wall-0 ✅ 0.61 | wall-0+wall-1 ✅ 0.68           | wall-0+wall-1 ✅ 0.91                                    |

Confidence calibration also improved with the annotated image: ambiguous groundings drop to
0.42–0.76 instead of asserting 0.9+, and `uncertain` relationships appear where identification
is unreliable.

## Verdict

**Yes — the annotated recognition image materially improves object-ID grounding.**
- Architectural understanding was already good and stays the same (rooms, continuity,
  false-positive detection).
- ID grounding improves measurably: the kitchen window host (window-3 → wall-4, previously wrong
  with 0.94 confidence), kitchen boundary (impossible wall-3 dropped), door-5 dual-segment hosts,
  terrace-vs-living distinction, and entry-door grounding all became correct or cleaner.
- Residual risk: grounding is still not perfect (run 1 still mis-grounded window-3), so the
  `uncertain` + confidence rules remain essential; run-to-run variance exists and the schema
  now makes that variance visible instead of hiding it behind high confidence.

## Reproduce

1. Start the frontend (`:3000`) and expose-service (`:4000`, `OPENAI_API_KEY` set).
2. Open `/debug/floorplan-recognition`, click **Load fixture**.
3. Inspect the **Annotated Recognition Image** panel (Original vs Annotated) before invoking the VLM.
4. Click **Analyze with VLM** — the page posts original image + annotated PNG + raw JSON to
   `/api/debug/floorplan-recognition/vlm-analysis` and renders findings, grounding list, and overlay.
